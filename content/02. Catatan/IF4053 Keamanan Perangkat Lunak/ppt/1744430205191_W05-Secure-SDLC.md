Risk Assessment

• Identifies, analyzes, and prioritizes potential risks to the software

system.
• Steps:

• Identify assets (e.g., user data, intellectual property).
• Identify threats (e.g., unauthorized access, data breaches).
• Identify vulnerabilities (e.g., lack of encryption, weak

authentication).

• Assess risk by evaluating likelihood and impact.
• Prioritize risks based on severity.

• Outcome: A list of prioritized risks to address in the development

process.

Security Requirements

• Define specific, measurable guidelines to ensure software security.
• Types:

• Functional Security Requirements: Features like authentication,

encryption, and logging.

• Non-Functional Security Requirements: Attributes like resilience,

availability, and compliance.

• Derived from:

• Risk assessment findings.
• Legal and regulatory standards (e.g., GDPR, PCI-DSS).
• Industry best practices (e.g., OWASP guidelines).

• Outcome: A comprehensive list of security requirements to guide design,

implementation, and testing.

Secure Design Principles Overview

▪ Secure design principles guide the development of robust and secure

software:
▪ Least Privilege: Grant only the minimum access necessary.
▪ Fail-Safe Defaults: Default to secure states when errors occur.
▪ Separation of Duties: Divide responsibilities to reduce insider threats.
▪ Defense in Depth: Use multiple layers of security to protect against

threats.

▪ Economy of Mechanism: Keep designs simple to reduce errors.
▪ Complete Mediation: Ensure all access requests are checked for

authorization.

▪ Open Design: Rely on the strength of the design, not secrecy.

Foundation in Secure-Design

• Reduce the attack surface.
• Minimize the impact of vulnerabilities.
• Ensure software is resilient to attacks.

Principles in Practice

•

•

Least Privilege:
• A database user account only has read access, not write access.
Fail-Safe Defaults:
• A system denies access by default unless explicitly allowed.

• Separation of Duties:

• Developers cannot deploy code directly to production; a separate team handles deployment.

• Defense in Depth:

• A web application uses HTTPS, a web application firewall (WAF), and input validation to protect against

attacks.

•

Economy of Mechanism:
• A simple authentication mechanism reduces the risk of implementation errors.

• Complete Mediation:

• Every API request is checked for proper authentication and authorization.

• Open Design:

• Cryptographic algorithms are open and peer-reviewed, rather than relying on secrecy.
